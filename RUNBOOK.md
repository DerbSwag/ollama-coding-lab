## Evidence and interpretation

Each invocation uses its own ignored `.evidence/phase3-<UUID>/` directory:

| File | Meaning |
| --- | --- |
| `phase3.json` | Explicit PASS/FAIL/BLOCKED/NOT_RUN checks, source hashes, immutable image IDs, layer identities and linked artifact hashes |
| `commands/*.json` | Executed argument list, stdout, stderr, child exit/signal/error and duration; no environment dump |
| `sbom.cdx.json` | CycloneDX 1.7 generated by pinned Trivy from the exported image |
| `image-vulnerabilities.json` | HIGH/CRITICAL vulnerability report from the same archive |
| `image.tar` | Local export retained for reproduction; never uploaded by the workflow |
| `cache/` | Run-specific scanner cache; never uploaded by the workflow |

On Docker's containerd image store, the Docker image identity can be an OCI index
digest, while Trivy reports the image configuration digest. They need not be equal.
The script verifies rootfs DiffIDs and the unique run label against both reports,
matches the SBOM's config digest to the vulnerability report, and rehashes the
archive. This is unsigned local provenance, not a registry signature/attestation.

Image policy: HIGH/CRITICAL findings cause FAIL with exit 1. Unexpected scanner
exit, missing/malformed report, absent OS coverage or unverifiable provenance is
BLOCKED. Contradictory JSON/exit codes cannot pass. No ignore-unfixed exception is
used. SBOM generation with exit 0 is inventory only; the separate scan is mandatory.

When a prerequisite is unavailable, dependent checks remain NOT_RUN; overall exit
is 1. Read the JSON and command records; stderr by itself is not a failed process.
Existing static gate uses its original pass/findings/error vocabulary and policy.

## Cleanup, failure and recovery

Cleanup attempts every exact owned container name and checks the matching run label
before removal; missing containers are harmless, removal errors fail validation.
Only containers created for the current UUID are touched. No image/container/volume
prune, wildcard deletion, image removal or changes to unrelated resources occur.
Images, exports and caches intentionally remain for inspection.

If Docker disappears, restore the Engine normally, inspect `phase3.json` and list
only the relevant ownership label:

```powershell
# Replace this with the exact runId from your report, not a guessed/global filter.
$validationRunId = '<exact-runId>'
docker ps -a --filter "label=org.ollama-coding-lab.validation=$validationRunId"
```

For leftover containers after an uncatchable interruption, inspect each exact name
and its label, then remove that specific owned container if approved. Do not use
global `docker system prune`, `docker container prune`, or bulk label deletion.
For normal runs cleanup is automatic. The script's stop/start recovery test affects
only its own demo container, which is removed when validation finishes.

## Rollback

No service is deployed. Images are uniquely tagged; previous images remain intact.
To inspect a previously passing result, use its exact `imageTag`/`imageId` and JSON
evidence. Any manual run must keep loopback-only publishing and the verified flags.
Stop only that manually created container by its exact ID/name when finished.

Source changes are uncommitted. Preserve the diff and obtain authorization before
restoring selected source files or creating a revert commit. Do not use reset/clean
or overwrite unrelated changes. No source rollback was executed; container recovery
and startup-failure cleanup were actually tested.

## CI and limitations

Original Windows/Linux contracts and Static Analysis Gate remain unchanged. A new
Container Runtime and Supply Chain job requires Static Analysis Gate success and
uploads allowlisted JSON/SBOM evidence with 7-day retention even on failure. Hard
cancellation before evidence creation can leave incomplete artifacts. No raw archive
or database cache is uploaded. Review evidence paths/metadata before sharing.

Phase 3 GitHub-hosted execution is NOT_RUN pending explicit authorization to publish
the changes. After the first successful hosted run, require the new Container Runtime
and Supply Chain check in addition to existing required checks; no branch protection
settings are changed by this implementation. Multi-architecture execution, publisher signature validation, full SBOM
schema certification, load testing, persistent-data migration and production rollback
are not verified. The pinned image can acquire new CVEs as databases change; rerun
the same policy and update reviewed digests when needed rather than suppress findings.
